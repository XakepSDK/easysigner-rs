# Android app in Kotlin + Compose: plan

The native-UI TODO in `android-plan.md`, made concrete for the simple redesign (24 phone
screens, final as of 2026-11-23). Screen numbers below are the design's (1 Home, 2 Add key,
3 Sign, 4 Signed, 4b Who signed page, 5 Check valid, 6 Do not trust, 7 Your keys, and their
letter variants). The design's rules note is the behaviour spec; this file is how to build it.

## Shape

- **Rust core, one library.** Everything that decides: formats, signing, NCA calls, checks,
  the key vault, the PDF "Who signed" page. No UI text except what goes into files (stamp
  and page text, in Kazakh, Russian and English).
- **`ffi` crate** (new, `cdylib`): the UniFFI surface below, nothing else. Built for
  `arm64-v8a` and `x86_64` (emulator) with `cargo ndk`; Kotlin bindings generated by
  `uniffi-bindgen` at build time, not checked in.
- **Android app** (`android/`): one activity, Kotlin, Jetpack Compose, Material 3,
  Navigation Compose. All screen text in Android string resources (kk, ru, en).
- **Desktop** stays on egui over the same core.
- The egui Android build (GameActivity, the IME bridge, AccessKit glue) is removed once the
  Compose app covers every screen; until then both build in CI.

## Core API for the screens (UniFFI)

The core returns facts and codes; the app picks the words. Calls that touch the network block
and are called from `Dispatchers.IO`.

| Call | Feeds screens | Returns |
|---|---|---|
| `inspect(name, bytes)` | routing after Share or a file pick; 3, 3b, 3d, 3g, 5c | file kind (PDF with page count, .cms with inner name, XML, other with MIME), existing signers with a quick validity, what signing will produce |
| `keys()` | 1, 3, 7 | per key: name, IIN, company, BIN, role, expiry, `can_sign` or why not (expired, revoked, GOST 2004) |
| `add_key(p12, password)` | 2, 2b, 2c | key id, or `WrongPassword { latin_retyped }`, `NotAKey`, `CantSign(reason)` |
| `remove_key(id)` | 7b | — |
| `sign(id, name, bytes)` | 3–4, 3c, 3e, 3f, 3g | signed bytes, output name, NCA time; or `Offline`, `NcaUnreachable`, `KeyRevoked`, `KeyExpired`, `Gost2004`, `Cancelled` |
| `check(name, bytes)` | 5, 5b, 5d, 5e, 6, 6b, 6c | overall `Valid / Invalid(reason) / Unknown / NotSigned`, per signer: name, IIN, company, BIN, role, time and whether NCA confirmed it, key expiry; details for 5d |

Key unlock: the vault's `Guard` trait becomes a UniFFI callback interface implemented in
Kotlin with `BiometricPrompt` + a Keystore AES key (StrongBox when present), replacing the
string protocol between `src/android.rs` and `KeyGuard.java`. Same Keystore aliases and vault
file, so keys added in the egui build survive the switch. No screen lock: the password path
(3e) as today.

## Core changes the design needs

Most of the behaviour exists; these are new or different:

1. **Output by input**: PDF → PAdES, XML → XAdES, received .cms → co-sign, anything else →
   attached CAdES. No options reach the UI (today the GUI offers detached, card, levels).
2. **Who signed page** (4b) replaces the corner stamp in `src/pdf/stamp.rs`: the first signer
   appends an A4 page with the trilingual note and footer links; each signer's box is that
   signature's widget appearance, in two columns, placed below every existing widget on the
   page (NCALayer's too) and never overlapping one; 20 fit. Full page: one note line, then
   invisible signatures. A PDF signed elsewhere with no such page: empty margin only, else
   invisible.
3. **Lock after the first signature**: certification signature, DocMDP P=2. The existing
   check (`changes_after`) already turns anything but signatures after a signature red.
4. **Pre-sign gate**: refuse GOST 2004 keys and keys NCA reports revoked or unknown, before
   any prompt (`sign::check_key` does the OCSP part).
5. **No NCA time** (5e, 6c): signatures without a timestamp are checked as of now; the report
   carries the signer key's expiry and a distinct "expired since" reason.
6. **Reasons as codes**: `report::SignerReport` gets a reason enum (changed, revoked,
   expired, expired since, not recognized in Kazakhstan, damaged, couldn't confirm) next to
   today's text.

## Android pieces

- **Files in**: `ACTION_SEND` / `ACTION_VIEW` intent filters (Share from Telegram, WhatsApp,
  files apps); a file shared before any key exists goes to Add key, then back (2c).
- **Files out**: Send through the share sheet; Save to phone through SAF `CreateDocument`.
- **Read it**: PDFs and pictures shown in-app with `PdfRenderer`; other types open with
  `ACTION_VIEW`, and Sign unlocks when the app comes back (3b).
- **Wording follows the lock**: fingerprint, screen lock or password, from
  `BiometricManager.canAuthenticate`.
- **Language**: per-app language (`LocaleManager`), set from Your keys; default follows the
  phone.
- **Accessibility**: Compose semantics, 48 dp targets, font scaling to 200 %, TalkBack
  labels on icon buttons.
- minSdk 30, targetSdk 35, compileSdk as now.

## Tests

- Core: existing unit and e2e tests (fake TSA and OCSP), plus the new PDF page layout,
  DocMDP, placement next to NCALayer-style widgets, and the no-timestamp path.
- App: Compose UI tests per screen on the emulator in CI, driving the real core with the
  fake NCA endpoints; the UI Automator flow kept for the end-to-end path (share in, sign,
  fingerprint, send) and the TalkBack walk.

## Phases

1. **Skeleton**: split the core from the egui crate, add `ffi`, generate bindings, a Compose
   app that lists keys; CI builds both apps.
2. **Keys**: 2, 2b, 2c, 7, 7b, 7c, 3e; Kotlin `Guard` with `BiometricPrompt`; migration test
   from the egui build's vault.
3. **Sign**: 1, 3, 3b, 3c, 3d, 3f, 3g, 4 with today's signing.
4. **Check**: 5, 5b, 5c, 5d, 5e, 6, 6b, 6c.
5. **Core changes 2–6** above (desktop gets them too), with 4b.
6. **Finish**: remove the egui Android build, accessibility pass, Pixel check, release.

## Not decided here

- UniFFI and Compose BOM versions: the newest at the start of phase 1.
- Whether desktop also drops its option-rich screens for the simple flow.
- Pricing (affects the footer's "free" and About's "no accounts, no tracking").

## Where phase 1 ended

- `ffi/` (`kzsigner-ffi`): `version()` and `list_keys(vault_path)` over UniFFI 0.32, with the
  core as `default-features = false` (no egui). Its tests run in CI as their own step, because
  the workspace's `default-members` is the core alone.
- The Kotlin + Compose app is `android/compose`, applicationId `kz.kzsigner.next`, so it
  installs next to the egui app until it replaces it (phase 6). Compose BOM 2026.11.01,
  Material 3, `compileSdk` 37.2 (Compose 1.13 asks for 37.1 or newer, so all three modules
  moved). Its keys screen reads the vault through the core; text is in `res/values{,-ru,-kk}`.
- `scripts/apk.sh` builds both APKs: it generates the Kotlin bindings with `uniffi-bindgen`
  from a host build of the library (the release `.so` is stripped of what the generator reads)
  and keeps them out of the repository. `dist/kzsigner-next-<version>-android.apk` is not part
  of a release.
- The emulator job runs `ComposeApp` (android/uitest): the app starts and its keys screen
  shows "No keys yet", which only a working UniFFI call can produce.

## Where phase 2 ended

- The core's `Vault` object (ffi): `keys()` with each key's unlock and why it can't sign
  (expired, not valid yet, GOST 2004; revocation is checked when signing), `add_key`,
  `remove_key`, `unlock` for a list hidden in the egui app, `new_key_unlock`. `add_key` says
  why a file was refused (`WrongPassword`, `NotAKey`, `KeyCantSign`, `AlreadyAdded`,
  `Cancelled`) and checks those before any prompt. `p12::problem` tells a wrong password
  from a file that is not a key.
- The chip is the UniFFI foreign trait `Chip`, implemented by `KeystoreChip.kt`: a port of
  KeyGuard.java with the same key parameters and the same sealed layout, so the vault file
  moves over unchanged. The Rust test `reads_the_egui_apps_vault` checks a vault written by
  the egui side, hidden list included, opens through the app's chip.
- Screens 2, 2b, 3f (when adding), 7, 7b and 7c, after the design. The app opens on Your
  keys, or on Add key when there are none; Home comes with signing. "Open with kzsigner" on
  a .p12 goes to Add key with the file chosen.
- Language: AppCompat's per-app language (Android 11 and 12 need it; 13+ have it built in),
  so the activity is an `AppCompatActivity`.
- Moved to phase 3, where the file comes in: 2c (a shared document before any key) and 3e
  (signing with the password on a phone with no screen lock). The password path itself
  works already: a key added on such a phone is kept under its own password.
- Emulator: `ComposeApp` opens test keys from the test APK (`KeyFiles`), checks the GOST
  2004 screen, the wrong-password hint for a Russian keyboard, adds the key with a touch of
  the fingerprint sensor, and removes it.

## Where phase 3 ended

- Core (ffi): `inspect(name, bytes)` says what a file is (PDF, XML, .cms, key file, other),
  who signed it already (name, company, time; their validity is phase 4's), and what signing
  makes (`InsidePdf`, `InsideXml`, `NewCms`, `JoinCms`, or `Cannot` for a detached .cms or an
  XML document another signature would break), with the output's name. `Vault.sign` checks
  the key with NCA before any prompt (expired, not yet valid, GOST 2004, not NCA's,
  revoked, or no answer from NCA), then opens it (one prompt, or the key's password) and signs
  as the desktop app does by default: with NCA's time, made long-term (LTA). It returns the
  file, its name and NCA's time. `Nca` holds the servers and trust; tests make one with the
  fake servers, which moved to `tests/common/nca.rs` so the core and ffi tests share them.
- `CantSign` gained `Revoked` and `NotRecognized`, found when signing.
- Screens 1, 3, 3b (Sign unlocks once the file was opened in its app), 3c (no internet, or
  NCA not answering, told apart with the phone's connectivity), 3d, 3e, 3f at signing time,
  3g, 4, and 2c. PDFs are read in the app with Android's `PdfRenderer`; other files open in
  the app that reads them, through a `FileProvider` copy in the cache. Send is the share
  sheet; Save to phone is the system's save dialog.
- The PDF still gets today's corner stamp on its last page (in the app's language), and the
  wording says so; the Who signed page is phase 5.
- Files come in with Share (`ACTION_SEND`, any type) and Open with (`ACTION_VIEW` for PDF,
  XML, CMS, Office, key files and octet-stream), up to 50 MB.
- Emulator: `ComposeApp` shares a PDF in, sees its first page and the reader, and signing
  with the test key stops at "isn't recognized" before any prompt (the test CA is not NCA's).
  After the key is removed, a shared PDF waits on Add key (2c) and comes back once a key is
  added. The Signed screen itself is reached only by the core's tests (fake NCA servers),
  not on the emulator.

## Where phase 4 ended

- Core (ffi): `check_file(nca, name, bytes, original, lang)` gives one verdict (`Valid`,
  `Invalid`, `Unknown` when NCA gave no answer, `NotSigned`, or `NeedsDocument` for a
  detached .cms) and, per signer, one `Reason` when theirs fails, the first that applies:
  `Changed`, `Revoked`, `NotRecognized`, `Damaged`, `Expired` (at NCA's time),
  `ExpiredSince` (no NCA time, and the key has expired since), `NotConfirmed`. The reason is
  read from the report's fields in the ffi crate, so the core's `SignerReport` is unchanged;
  phase 5's item 6 can move it into the core. Each signer carries NCA's time or the
  computer's, the key's dates and the details for 5d, in the app's language.
- Screens 5, 5b, 5c, 5d, 5e, 6, 6b, and 6c's reasons, plus "choose the document" for a
  detached .cms. Home's "Check a signature" opens a file to check; "Add my signature" and
  "Sign it myself" go on to Sign. The Sign screen's "Already signed by" rows now say whether
  each signature holds, once NCA has answered.
- Other apps (and the tests) can open the Check screens with the action
  `kz.kzsigner.action.CHECK` and a content:// file.
- Emulator: `ComposeApp` checks an unsigned PDF ("isn't signed") and a .cms signed with a
  test key ("do not trust", not recognized in Kazakhstan), and opens its details. A valid
  verdict needs NCA's real keys, so it is reached only by the core's tests (fake NCA).

## Where phase 5 ended

- **Who signed page** (`src/pdf/whosigned.rs`, `Engine::sign_pdf_page`): the first signer
  appends an A4 page (trilingual title and note, footer listing the apps as plain text until
  store links exist) and draws their box in the grid's first spot. Later signers take the
  first spot after the last one used, clear of every widget and below the lowest widget
  another app placed on the page. Twenty boxes in two columns, then one note box across the
  page, then invisible signatures. Each box is the signature's own widget appearance: name,
  company and BIN or IIN, and the signing time in Astana time, marked as NCA's when a
  timestamp backs it. The desktop's option and the app both use it.
- **Departure from the plan**: a PDF that someone signed elsewhere first (no Who signed
  page) gets an invisible signature. Finding an empty margin reliably needs content
  analysis, and a box over the document's text is worse than none.
- **DocMDP P=2**: the first signature certifies the PDF when it adds the page (no earlier
  signatures and no certification already there), so a viewer flags anything but signatures
  and form filling after it; the change check already turned such changes red.
- **Reasons as codes**: `SignerReport::reason()` in the core gives the `report::Reason`;
  the app's `Reason` maps from it one to one.
- **Pre-sign gate and "expired since"**: done in phases 3 and 4 for the app (ffi). The
  desktop keeps today's behaviour.
- The app tells the signer about the page (Sign screen wording, "N pages + Who signed page"
  on the document card, and "your name is added next to …" when joining).
- Tests: `tests/who_signed.rs` (page and certification, second box placement, another app's
  stamp, 20 boxes then the note then invisible, a PDF signed elsewhere, changes after
  signing caught). Set `KZ_WHO_SIGNED_OUT=file.pdf` to write a three-signer sample.

## Where phase 6 ended

- The Compose app is the Android app: `android/compose`, applicationId `kz.kzsigner`,
  version code 2, signed with the same key as the egui build, so it installs over it and
  opens its keys (same vault file, same chip keys). Kotlin package `kz.kzsigner`.
- Removed: the egui Android library (`android/src`, `src/android.rs`, the self-test copy),
  its Java side, the `selftest` feature and the `jni-macros` patch. `scripts/apk.sh` builds
  `dist/kzsigner-<version>-android.apk`; `KZSIGNER_UITEST=1` also builds the emulator tests.
  The release job publishes that APK with the desktop downloads.
- The app now asks for INTERNET (the egui build did; the Compose app had missed it, so it
  could not reach NCA outside the emulator's chain check).
- Emulator tests (`AppFlows`, Android 11, 15, 16): they set up the screen PIN and a finger
  themselves; each screen they visit is checked for accessibility (every control named for
  TalkBack, at least 48 dp); Home, Sign and Your keys run with text at 200 %; a
  fingerprint-only key is reset when another finger is enrolled.
- Compared with the design screens: layouts match. Large text broke the Home title and
  clipped "Remove from this phone"; both fixed.
- Left for a person: a check on a real phone with a hardware key chip (emulators keep keys
  in software, so they use the key's password), a native speaker's read of the Kazakh and
  Russian texts, the release signing key in the CI secrets, and the version bump that cuts
  the release.

## After phase 6: Home is the only landing page

- The app always opens on Home, with or without a key. With none, the key chip reads "Add
  key", and "Sign a document" opens Add key first ("To sign, first add your key... then
  choose the document"): the file picker can't say which of two files it wants, so the key
  comes first, then the document picker opens by itself. With a key, the picker opens
  directly. A document shared with no key goes to Add key with the document waiting (2c),
  then on to Sign. Checking never
  needs a key. Removing the last key goes back to Home. (Earlier the app opened on Add key
  when there was none, which hid Check and repeated Add key as a second home.)
- Adding a key refuses one not from NCA or another CA recognized in Kazakhstan, offline,
  before any prompt. The emulator tests run the "uitest" build type, which also trusts the
  test keys' CAs when adding a key; the released APK doesn't.
