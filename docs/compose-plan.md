# Android app in Kotlin + Compose: plan

The native-UI TODO in `android-plan.md`, made concrete for the simple redesign (24 phone
screens, final as of 2026-11-23). Screen numbers below are the design's (1 Home, 2 Add key,
3 Sign, 4 Signed, 4b Who signed page, 5 Check valid, 6 Do not trust, 7 Your keys, and their
letter variants). The design's rules note is the behaviour spec; this file is how to build it.

## Shape

- **Rust core, one library.** Everything that decides: formats, signing, NCA calls, checks,
  the key vault, the PDF "Who signed" page. No UI text except what goes into files (stamp
  and page text, in Kazakh, Russian and English).
- **`ffi` crate** (new, `cdylib`): the UniFFI surface below, nothing else. Built for
  `arm64-v8a` and `x86_64` (emulator) with `cargo ndk`; Kotlin bindings generated by
  `uniffi-bindgen` at build time, not checked in.
- **Android app** (`android/`): one activity, Kotlin, Jetpack Compose, Material 3,
  Navigation Compose. All screen text in Android string resources (kk, ru, en).
- **Desktop** stays on egui over the same core.
- The egui Android build (GameActivity, the IME bridge, AccessKit glue) is removed once the
  Compose app covers every screen; until then both build in CI.

## Core API for the screens (UniFFI)

The core returns facts and codes; the app picks the words. Calls that touch the network block
and are called from `Dispatchers.IO`.

| Call | Feeds screens | Returns |
|---|---|---|
| `inspect(name, bytes)` | routing after Share or a file pick; 3, 3b, 3d, 3g, 5c | file kind (PDF with page count, .cms with inner name, XML, other with MIME), existing signers with a quick validity, what signing will produce |
| `keys()` | 1, 3, 7 | per key: name, IIN, company, BIN, role, expiry, `can_sign` or why not (expired, revoked, GOST 2004) |
| `add_key(p12, password)` | 2, 2b, 2c | key id, or `WrongPassword { latin_retyped }`, `NotAKey`, `CantSign(reason)` |
| `remove_key(id)` | 7b | — |
| `sign(id, name, bytes)` | 3–4, 3c, 3e, 3f, 3g | signed bytes, output name, NCA time; or `Offline`, `NcaUnreachable`, `KeyRevoked`, `KeyExpired`, `Gost2004`, `Cancelled` |
| `check(name, bytes)` | 5, 5b, 5d, 5e, 6, 6b, 6c | overall `Valid / Invalid(reason) / Unknown / NotSigned`, per signer: name, IIN, company, BIN, role, time and whether NCA confirmed it, key expiry; details for 5d |

Key unlock: the vault's `Guard` trait becomes a UniFFI callback interface implemented in
Kotlin with `BiometricPrompt` + a Keystore AES key (StrongBox when present), replacing the
string protocol between `src/android.rs` and `KeyGuard.java`. Same Keystore aliases and vault
file, so keys added in the egui build survive the switch. No screen lock: the password path
(3e) as today.

## Core changes the design needs

Most of the behaviour exists; these are new or different:

1. **Output by input**: PDF → PAdES, XML → XAdES, received .cms → co-sign, anything else →
   attached CAdES. No options reach the UI (today the GUI offers detached, card, levels).
2. **Who signed page** (4b) replaces the corner stamp in `src/pdf/stamp.rs`: the first signer
   appends an A4 page with the trilingual note and footer links; each signer's box is that
   signature's widget appearance, in two columns, placed below every existing widget on the
   page (NCALayer's too) and never overlapping one; 20 fit. Full page: one note line, then
   invisible signatures. A PDF signed elsewhere with no such page: empty margin only, else
   invisible.
3. **Lock after the first signature**: certification signature, DocMDP P=2. The existing
   check (`changes_after`) already turns anything but signatures after a signature red.
4. **Pre-sign gate**: refuse GOST 2004 keys and keys NCA reports revoked or unknown, before
   any prompt (`sign::check_key` does the OCSP part).
5. **No NCA time** (5e, 6c): signatures without a timestamp are checked as of now; the report
   carries the signer key's expiry and a distinct "expired since" reason.
6. **Reasons as codes**: `report::SignerReport` gets a reason enum (changed, revoked,
   expired, expired since, not recognized in Kazakhstan, damaged, couldn't confirm) next to
   today's text.

## Android pieces

- **Files in**: `ACTION_SEND` / `ACTION_VIEW` intent filters (Share from Telegram, WhatsApp,
  files apps); a file shared before any key exists goes to Add key, then back (2c).
- **Files out**: Send through the share sheet; Save to phone through SAF `CreateDocument`.
- **Read it**: PDFs and pictures shown in-app with `PdfRenderer`; other types open with
  `ACTION_VIEW`, and Sign unlocks when the app comes back (3b).
- **Wording follows the lock**: fingerprint, screen lock or password, from
  `BiometricManager.canAuthenticate`.
- **Language**: per-app language (`LocaleManager`), set from Your keys; default follows the
  phone.
- **Accessibility**: Compose semantics, 48 dp targets, font scaling to 200 %, TalkBack
  labels on icon buttons.
- minSdk 30, targetSdk 35, compileSdk as now.

## Tests

- Core: existing unit and e2e tests (fake TSA and OCSP), plus the new PDF page layout,
  DocMDP, placement next to NCALayer-style widgets, and the no-timestamp path.
- App: Compose UI tests per screen on the emulator in CI, driving the real core with the
  fake NCA endpoints; the UI Automator flow kept for the end-to-end path (share in, sign,
  fingerprint, send) and the TalkBack walk.

## Phases

1. **Skeleton**: split the core from the egui crate, add `ffi`, generate bindings, a Compose
   app that lists keys; CI builds both apps.
2. **Keys**: 2, 2b, 2c, 7, 7b, 7c, 3e; Kotlin `Guard` with `BiometricPrompt`; migration test
   from the egui build's vault.
3. **Sign**: 1, 3, 3b, 3c, 3d, 3f, 3g, 4 with today's signing.
4. **Check**: 5, 5b, 5c, 5d, 5e, 6, 6b, 6c.
5. **Core changes 2–6** above (desktop gets them too), with 4b.
6. **Finish**: remove the egui Android build, accessibility pass, Pixel check, release.

## Not decided here

- UniFFI and Compose BOM versions: the newest at the start of phase 1.
- Whether desktop also drops its option-rich screens for the simple flow.
- Pricing (affects the footer's "free" and About's "no accounts, no tracking").
